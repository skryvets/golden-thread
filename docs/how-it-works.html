Golden Thread · how it works

One vault, re-read every turn.

Golden Thread is a Claude Code plugin that gives every AI session you run one shared memory, an Obsidian vault of plain markdown, and then makes sure the rules in that vault are actually followed. Eight scenes below show the two problems it solves and the machinery that solves them. Drag the stage to look around.

Problem 1 · scene 1 of 8

Every session starts with amnesia

Claude Code keeps nothing between sessions. You open a project, explain the conventions, the session learns three things about the deploy path, and then it ends. The next session starts blank.

What survives is whatever you wrote by hand into a .claude/memory/ folder or a CLAUDE.md, per project, in whichever shape you used that day. Three projects mean three scattered piles, and a finding from one project never reaches the other two.

three projects, sessions flicker in and out above them, and the facts each session learned drift off and fade.

Problem 2 · scene 2 of 8

Writing a rule down does not mean it is followed

This is the problem most memory systems skip. A rule can sit in a loaded CLAUDE.md for a whole session and still be dropped for dozens of turns. It was never deleted. The task in front of the model simply crowded it out of attention.

"In context" is not "applied". The repository states its governing law in one line, and everything in the plugin follows from it:

A Core rule is only as durable as the mechanism that re-asserts it. Storing a rule in a file is not enforcement; the file may never be read.

a context window fills with the work of the session, and the rules loaded at the start dim as they are pushed out of attention.

Answer 1 · scene 3 of 8

One vault, shared by every session

Golden Thread points every session at one Obsidian vault: a folder of markdown files under git. The pointer lives in ~/.claude/vault-config.json, so every project and every session finds the same place.

Sessions read from the vault at startup with /gt:gt-open, look things up while working with /gt:gt-query, and write back what they learned at the end with /gt:gt-work. The session dies. The vault does not. That connection is the golden thread.

the same three projects, now tied to a vault. Sessions still come and go, but their facts flow into the vault and come back out at the next start.

Answer 1 · scene 4 of 8

Facts climb a ladder and never come back down

Inside the vault, knowledge sits at one of five levels. A finding lands in a project's memory/. If it holds, it moves into the project's research.md or decisions.md. If it applies beyond that project, it becomes a Knowledge/ page. If every session needs it, it reaches global-memory/.

/gt:gt-promote moves a fact up. Nothing moves down and nothing is silently deleted. Some files are immutable by design: the Sources/ originals behind Knowledge pages and each project's idea.md. research.md and decisions.md are append-only.

the vault opened into its five tiers. One fact climbs from the session floor to global memory; the locked files sit beside the tiers they protect.

Answer 1 · scene 5 of 8

Opening a project is cheap on purpose

/gt:gt-open reads a project's documents in a fixed order: source, idea, research, decisions, design, spec, runbook. Then it reads only memory/MEMORY.md, an index with one line per memory file, and stops.

Memory files load on demand, when the task touches their subject. A project with 40 memory notes costs about 45 lines to open instead of about 2,000, which leaves the context window for the actual work. That is why the one-line descriptions in the index matter: they are the whole basis for deciding what is worth opening.

the seven documents light up in reading order, then the index. The shelf of memory files stays dark until one is asked for.

Answer 2 · scene 6 of 8

Core rules are re-asserted on every turn

Every rule in the vault carries a scope (core, context, generic) and an enforcement strength (reminder or validated). A Core rule is not trusted to a file.

A UserPromptSubmit hook, inject_core_rules.sh, runs before the model sees each prompt. It reads core-rules/*.md from the vault at that moment and injects each rule's imperative, plus the current timestamp, into the turn. Edit a rule file and the next turn injects the new text; no rule text is ever copied into the script. If the vault cannot be reached, the hook announces the degraded state loudly instead of going quiet.

one turn as a loop. The prompt passes the inject gate, which pulls the rules down the thread from the vault and sends them along with the prompt to the model.

Answer 2 · scene 7 of 8

Validated rules are checked, not just reminded

A reminder still depends on the model's discipline. Five rules are validated: a hook inspects what is about to happen and blocks it. Three PreToolUse guards deny a write to a vault file another live session has claimed, a vault-mutating command that does not name its vault, and a git commit of code whose tests have not been seen to pass. The Stop hook reads the finished reply and blocks it if it leaks a secret or does not begin with the timestamp.

The timestamp is the canary. It costs nothing and it is visible on every reply, so when it disappears you know enforcement broke. Every guard fails open: anything it cannot parse is allowed, because a guard that blocks wrongly gets switched off, and then it guards nothing.

the same loop. The guard gate turns a bad tool call away; the stop gate bounces a reply without its timestamp back to the model, then lets the corrected one through.

Answer 2 · scene 8 of 8

The plumbing is built to survive renames

Hooks install to ~/.claude/golden-thread/hooks/, outside the vault, and ~/.claude/settings.json points at them by absolute path. The rules stay in the vault and are found at run time by gt_paths.py: the recorded path first, then a search for the folder that holds core_rule_priority_model.md, which it then re-records. Rename a project or move the vault and the hooks keep firing.

Two checks keep the whole thing honest. gt_lint.py has a core-unenforced check for a rule that is stored but wired to nothing, the exact failure the system exists to close. And the release gate proves wiring by installing into a throwaway home and asking every shipped hook where it ended up, rather than by reading the installer.

the pointers. Settings finds the hooks; the hooks find the vault; the vault moves and the thread follows. One rule with no wiring is flagged.

The same system, as a reference

Everything above in tables, for when you come back to look something up.

One session, start to finish

/gt:gt-open my-project     read docs in order, index memory, summarise
   …work…
/gt:gt-route               mid-session: what has this become, where does it belong
   …work…
/gt:gt-work                write findings, ADRs, design changes back to the vault

periodically
/gt:gt-lint                broken links, orphans, unenforced Core rules
/gt:gt-doctor              version, hook wiring, pending migrations, one report
/gt:gt-promote             move a fact up the ladder
/gt:gt-review              file the inbox into projects

Three hook points in every turn
